# Training

Three components get trained: the bi-encoder (Stage 2a), the cross-encoder (Stage 2b), and the GBM (Stage 3). All three share two non-negotiable constraints: no external data anywhere in the loop, and every fine-tuned artifact must survive the France generalization test (validated on a held-out country, never assumed from literature alone).

## Bi-encoder (Stage 2a)

**Candidate base models:** BGE-M3's dense head, or Qwen3-Embedding-0.6B. Both are MIT/Apache-2.0, both well under the 8B ceiling. Which one is used in production is decided empirically (see [`08_open_decisions_log.md`](08_open_decisions_log.md)) — the two differ architecturally (bidirectional encoder vs. decoder with last-token pooling), which is a genuine, not cosmetic, difference: target module names differ (`query`/`key`/`value`/`dense` vs. `q_proj`/`k_proj`/`v_proj`/`o_proj`/`gate_proj`/`up_proj`/`down_proj`), and pooling strategy must never be changed from what each model was pretrained with.

**Data construction.** Positive pairs: every `(S1, S2/S3)` pair in `train_ground_truth`. Hard negatives: mined from the blocking stage's *own* output — top-K candidates per S1 entity that are not in ground truth — rather than synthetic negatives, so training difficulty matches real inference-time difficulty. Every mined negative gets a manual review pass on a sample (~50-100 per country) to catch false negatives, since a mislabeled hard negative actively teaches the wrong thing. Balanced across source (S2/S3) and country, and includes some true singleton entities paired with their nearest (still false) candidates so the model learns what "confidently no match" looks like.

**Batch composition — not yet a fixed value, flagged here rather than left implicit.** MNRL's effectiveness depends on how many hard negatives accompany each positive within a batch, not just on hard negatives existing in the dataset at large. Too few and the loss falls back on easy in-batch negatives, weakening the hard-negative signal the mining step exists to provide; too many hard negatives per positive can destabilize early training, since the model hasn't yet learned enough to make fine distinctions among them. This ratio belongs in the same held-out-country validation grid as the rest of this file's open items — see [`08_open_decisions_log.md`](08_open_decisions_log.md) — rather than being set from a generic default.

**Loss.** `MultipleNegativesRankingLoss` (MNRL) with the mined hard negatives, using `CachedMultipleNegativesRankingLoss` to decouple effective batch size (and therefore negative count) from physical VRAM. **Not** raw triplet loss as the default — triplet loss can produce genuine, severe collapse depending on learning rate and setup (see [`07_citations_and_benchmarks.md`](07_citations_and_benchmarks.md)), though it has also been shown to work well in-domain for entity resolution specifically under a different, tuned configuration. Because MNRL optimizes ranking rather than the absolute cosine value the GBM will consume as a feature, pair it with either isotonic regression on a calibration slice or a CoSENT/AnglE loss trained toward the literal similarity target.

**Anti-forgetting (the France-generalization defense).** Primary: LoRA, applied across **all** linear layers (attention and FFN, not attention-only, not restricted to top-N layers), rank swept at 32/64/128 with rank-stabilized scaling — see [`05_regularization_and_anti_forgetting.md`](05_regularization_and_anti_forgetting.md) for the full reconciliation of this number against the original LoRA paper's own findings and a real scaling-factor confound that would otherwise bias the sweep toward under-rating higher ranks. LoRA's rank constraint is what structurally prevents the update from overwriting the pretrained multilingual structure the France generalization depends on. Secondary: a self-distillation anchor loss, comparing the fine-tuned model's embedding against the *frozen* base model's embedding on the same training text, weighted low (0.05–0.15) alongside the main loss — a compliant, no-external-data substitute for replay training. Tertiary: same-domain self-augmentation (character/field perturbations of your own records) for more effective positive diversity, never external sentence-pair datasets.

**Hardware (RTX 3060, 12GB).** bf16 throughout. Max sequence length capped at 64–96 tokens — business name/address strings are short, and training at the model's native multi-thousand-token ceiling wastes memory that should go to batch size. Physical mini-batch 32–64, effective batch (via caching) 256–512+.

**Evaluation.** Two-tier: a cheap proxy (margin/score-gap pass rate, Recall@K) drives early stopping within a run; the expensive confirmation — actual F₀.₅ through the full downstream pipeline — is computed once per candidate configuration, not per checkpoint. Both are run on the held-out-country split (train on US+India, hold out one as a France proxy), not a random split.

## Bi-encoder LoRA fine-tune — promoted from stretch goal to v1 scope

**Revision from the earlier v1 plan.** The original v1 scope cut LoRA fine-tuning entirely, reasoning that a dual-model (bi-encoder + Ditto), dual-tuning-method (LoRA vs. full), triple-rank ablation grid doesn't fit in 72 hours. That reasoning still holds for the *full* grid. It does not hold for a **single, pre-committed configuration** run once the hardware and time budget are confirmed — which is the actual situation now (RTX 3060 12GB confirmed, and enough time budgeted to use it). The distinction: this section commits to *one* rank, *one* layer-coverage rule, *one* regularization stack — not a sweep — specifically so it stays a same-day task rather than a research ablation.

**Target: BGE-M3's dense head, not Qwen3-Embedding-0.6B.** This reverses the original v1 pick for a specific, checkable reason: BGE-M3 is a bidirectional encoder (XLM-RoBERTa-based, 568M params) already pretrained on 100+ languages including French — fine-tuning it *adapts* pretrained multilingual structure it already has. Qwen3-Embedding-0.6B's advantage in [`07_citations_and_benchmarks.md`](07_citations_and_benchmarks.md)/[`01_v1_baseline_plan.md`](01_v1_baseline_plan.md) was specifically for the **off-the-shelf** comparison (its zero-shot French retrieval beats BGE-M3's zero-shot French retrieval). That comparison doesn't carry over once BGE-M3 is being fine-tuned on your own labeled pairs with an anti-forgetting stack designed to protect the exact capability that comparison was about — it's no longer "which model is better off-the-shelf," it's "does supervised adaptation of BGE-M3's own multilingual pretraining beat an un-adapted competitor." If time remains after this fine-tune lands, running the same off-the-shelf Qwen3-Embedding-0.6B feature *alongside* the fine-tuned BGE-M3 as a second Stage 2a-style feature is cheap (no training, just inference) and gives the GBM two independent signals rather than forcing a choice between them.

**Confirmed VRAM budget for a 3060 (12GB), computed directly rather than assumed:**

| Component | Size | Rank 32 | Rank 64 | Rank 128 |
|---|---|---|---|---|
| Base weights (bf16, frozen) | 568M params | 1.14 GB | 1.14 GB | 1.14 GB |
| LoRA trainable params | all linear layers, attn+FFN | 14.2M | 28.3M | 56.6M |
| LoRA optimizer state (AdamW: fp32 master + 2 moments) | — | 0.17 GB | 0.34 GB | 0.68 GB |
| **Fixed overhead total** | | **~1.3 GB** | **~1.5 GB** | **~1.8 GB** |

That leaves **~10GB** of the 3060's 12GB for activations, gradients, and batch — comfortably enough for `CachedMultipleNegativesRankingLoss` (which decouples effective batch/negative count from physical batch via gradient caching) at physical mini-batch 32–64, sequence length capped at 64–96 tokens (business name/address strings don't need more), with gradient checkpointing on to keep activation memory flat regardless of effective batch size. **Committed configuration: rank 64** — the middle of the previously-specified 32/64/128 sweep, chosen as a single value (not swept) because rank 64's optimizer overhead (0.34GB) is negligible relative to the 10GB headroom, so there's no VRAM reason to prefer 32, and going straight to 128 without the sweep that would justify it risks over-fitting the small labeled set without evidence it's needed. Rank-stabilized scaling (α/√r) applies since this is above the smallest previously-considered value.

**Committed fine-tuning config:**

```python
lora_config = {
    "r": 64,
    "lora_alpha": 64,              # with rank-stabilized scaling (α/√r), effective scale = 64/8 = 8
    "lora_dropout": 0.1,           # middle of the 0.05–0.1 range in regularization.md
    "target_modules": "all-linear", # attention (query/key/value/dense) + FFN — never attention-only
    "bias": "none",
}

training_config = {
    "loss": "CachedMultipleNegativesRankingLoss",
    "physical_batch_size": 48,      # mid-point of the 32–64 range, fits comfortably in the ~10GB headroom
    "mini_batch_size": 16,          # GradCache chunk size for the cached loss
    "max_seq_length": 80,
    "learning_rate": 2e-5,          # standard LoRA fine-tune LR for a sentence-transformer scale model
    "warmup_ratio": 0.1,
    "epochs": 3,                    # small labeled set — more risks overfitting given limited data volume
    "self_distillation_weight": 0.10,  # mid-point of the 0.05–0.15 range — see below
}
```

## France/multi-country regularization — the actual anti-forgetting stack, made concrete

This is the part that answers "how do we make sure fine-tuning doesn't hurt French generalization," which is the real risk of moving fine-tuning into v1 scope. Four mechanisms, layered — not alternatives to pick between:

1. **LoRA rank ceiling (structural).** Rank 64 with all-linear-layer coverage bounds the update to a low-rank perturbation of the pretrained weights — by construction, this can't fully overwrite the multilingual structure the base checkpoint already encodes, unlike full fine-tuning which can. This is the primary defense, and it's "free" in the sense that it's already the fine-tuning method, not an add-on.
2. **Self-distillation anchor loss (soft constraint).** During training, also compute the *frozen* base model's embedding on the same training text, and add an auxiliary loss term (cosine distance between fine-tuned and frozen embeddings) weighted at 0.10, alongside the main MNRL loss. This directly penalizes drift away from the pretrained embedding space — including on tokens/patterns the US/India training data never exercises, like French-specific vocabulary — even though the anchor loss itself is computed only on English/Hindi-script training text. It's a compliant, no-external-data substitute for replay training against a language you have no labeled examples of.
3. **Country-balanced hard-negative mining.** Hard negatives (top-K blocking candidates not in ground truth) must be balanced across US and India in the training batches — not just balanced across S2/S3 source, which was the original spec. An imbalanced mix (e.g. 90% US negatives) biases what "confidently no match" looks like toward US-specific noise patterns, which is exactly the shortcut-learning risk the country-match feature masking already guards against at the GBM layer — this is the same principle applied one layer earlier, at the encoder.
4. **Held-out-country validation as the actual gate, not a formality.** Train on US, validate on India (and the reverse), both directions, before trusting the fine-tune at all. If the held-out-country pass/margin rate is meaningfully worse than the in-domain rate, that's the direct evidence the anti-forgetting stack isn't sufficient — the fix is raising the self-distillation weight toward 0.15 or dropping rank toward 32 (less capacity to overfit US/India specifics), not proceeding anyway. This grid was already specified in [`08_open_decisions_log.md`](08_open_decisions_log.md); what's new here is treating it as a hard go/no-go gate for whether the fine-tuned checkpoint replaces the off-the-shelf feature at all, rather than an optional check.

**What this does not do:** it does not give the model labeled French examples — none exist in training data, and none should be synthesized (that would violate the no-external-data constraint if sourced from outside the competition's own files, and synthetic in-house perturbation of French text without any real French labels to validate against is guesswork dressed as data). The realistic goal is "don't damage the pretrained French competence already in the checkpoint," not "teach the model France." The held-out-country grid (US↔India) is the closest available proxy for measuring whether that goal is being met, precisely because no direct France measurement is possible before the real test set.

**Backbone: `xlm-roberta-base` (MIT, 279M params, 94 languages) — not Ditto's own documented defaults.** Ditto's reference implementation and paper support BERT, DistilBERT, RoBERTa, and ALBERT, all of which are English-pretrained in their standard checkpoints. Since Ditto's method is backbone-agnostic (plain sequence-pair classification via any transformer), swapping to `xlm-roberta-base` is a straightforward substitution, not a redesign — and it happens to share the same architecture family as BGE-M3, so the pipeline carries one fewer distinct base model to license-check and document.

**Serialization.** `[CLS] serialize(e) [SEP] serialize(e′) [SEP]` with `[COL]`/`[VAL]` tags per attribute. Domain-knowledge injection (span typing for informative fields) and TF-IDF-based summarization for long fields both operate purely on each record's own text — no external data involved.

**Data augmentation — MixDA.** Ditto's four operators (`del`, `swap`, `drop_col`, `append_col`) all transform the model's own labeled records, never external data. `drop_col` on the country attribute specifically implements the country-masking strategy used to stop the model over-relying on exact country match — this is not a separate mechanism bolted on, it's Ditto's own augmentation operator pointed at the right field. MixDA interpolates the *hidden representation* of the original and augmented example rather than swapping the augmented example in directly, because operators like `del` can be destructive enough to flip the true label (deleting the company name can leave nothing to distinguish a true match).

**Regularization.** Classification-head dropout set higher (0.2–0.3) than the encoder body's own dropout (kept near the 0.1 default, raised only if a held-out-country gap appears) — the head is trained from scratch on your labeled pairs alone and has no pretrained structure protecting it. LoRA rank is re-tuned independently for Ditto rather than reusing whatever wins for the bi-encoder — same 32/64/128 sweep as a starting grid, since binary classification over a joint sequence pair is a different task shape than contrastive ranking over independent embeddings (see [`05_regularization_and_anti_forgetting.md`](05_regularization_and_anti_forgetting.md)). `pos_weight` in the BCE loss, sized to whatever real imbalance is measured on the actual candidate set — Ditto trains on the same Stage 1 candidates, so this is computed once and reused, not a separately assumed value (see the GBM objective note below for why no fixed ratio should be hardcoded here). Same self-distillation anchor loss against the frozen `xlm-roberta-base` as the bi-encoder gets.

**Leakage-safe training.** Same 5-fold-holdout-plus-1-final-retrain cycle as the bi-encoder, if Ditto's score feeds the GBM as an out-of-fold feature.

## GBM (Stage 3)

**Objective:** `binary:logistic` with `scale_pos_weight` sized to the *true* imbalance ratio (roughly negative-count ÷ positive-count) — **computed from the real candidate set once `candidate_pairs.tsv` exists, not assumed.** (An earlier pass in this design used an illustrative `~1:65` figure elsewhere in these docs; that number was never measured against real data and should not be treated as a target — recompute it directly from your own blocking output before setting `scale_pos_weight`/`pos_weight` anywhere in this pipeline.) This is a learning-signal correction, not a precision lever — don't shrink it to "be more conservative"; that job belongs entirely to the Stage 4 threshold. Escalate to focal loss or a beta-weighted logloss only if validation shows the model isn't separating hard negatives well; if you do, **remove** `scale_pos_weight` rather than stacking it with a custom weighted objective — applying both compounds the same reweighting rather than adding two independent corrections. This isn't a theoretical risk: a documented real case on XGBoost's own community forum shows average precision collapsing from 0.65 to 0.03 on an imbalanced task after a practitioner combined `scale_pos_weight` with a custom weighted objective function computing the same correction twice — the forum's own reply was simply "remove `scale_pos_weight` ... since you are already applying the weight directly to the loss function." Same failure mode this design is guarding against, independently confirmed.

**Regularization:** shallow trees (`max_depth` 3–6), `subsample`/`colsample_bytree` at 0.7–0.8, `reg_alpha`/`reg_lambda` for L1/L2, and a deliberately tuned `min_child_weight` — without a floor here, boosting can carve a leaf that fits a handful of rare positive examples, which looks like good fit and is actually memorization given how few true positives exist relative to negatives.

**Monotonic constraints:** applied to every genuine similarity feature (name/address string similarity, both encoders' scores) so that higher similarity never predicts lower match probability. **Never** applied to the country-match flag — a monotonic constraint there would reintroduce the exact "same country ⇒ more likely match" shortcut the country-masking strategy exists to prevent.

**Country handling — the most important correctness rule in this stage.** Never feed raw country identity as a categorical feature. XGBoost's own documentation states plainly that an unseen category at inference has no valid encoding to fall back on, and the recommended fix — retraining — is exactly what's unavailable here, since France has zero labeled training rows. The only country-derived feature that reaches the GBM is a **symmetric, derived match/mismatch flag** computed by comparing two records' country fields; that computation works on France without the model ever needing to have "learned" the token, because the equality check happens upstream in feature engineering, not inside a learned categorical embedding. For a fraction of training rows, this match flag is deliberately replaced with a missing value — both XGBoost and LightGBM learn a sensible default split direction for genuinely missing values from the data present at training time, which is a controlled mechanism, unlike the unhandled-category failure mode above. This is the tabular equivalent of feature dropout, targeted specifically at the one feature most likely to become a shortcut.

**Early stopping and evaluation metric:** AUCPR, not plain logloss or accuracy — both are weak signals under heavy class imbalance (the actual ratio is measured, not assumed — see above), since a model that always predicts "no match" scores deceptively well on either. F₀.₅ itself is **not** used as a training/early-stopping metric, because it's macro-averaged per S1 entity (a set-level aggregate across a variable number of candidate rows), which doesn't map onto the row-level metrics GBM libraries expect. AUCPR drives model selection during training; F₀.₅ is computed only in the dedicated Stage 4 threshold search, after the GBM is otherwise finalized.

**Calibration:** isotonic regression after training, before threshold search — imbalance skews raw GBM probabilities, so this step isn't optional. One risk worth guarding against explicitly: isotonic regression is a flexible, non-parametric monotonic fit, which means it can itself overfit if calibrated on a small held-out set — a real concern here given the likely scale of labeled positives. Fit it via cross-validation (calibrate on out-of-fold predictions across multiple folds, the same pattern already used for the bi-encoder and Ditto's OOF scores) rather than a single train/calibration split, and fall back to Platt scaling — fewer effective parameters, less prone to overfitting on limited data — if the calibration set turns out too small for isotonic regression to be trustworthy. **Concrete rule of thumb, not just a qualitative caution:** the standard guidance is Platt scaling below roughly 1,000 calibration labels, isotonic regression above roughly 10,000, and fit-both-and-compare-by-held-out-loss in between. Given this design's likely scale (a candidate set already narrowed by blocking, with a small true-positive count relative to that), check which bracket the *actual* OOF positive count falls into before defaulting to isotonic — a small competition dataset can easily land in "Platt only" territory, in which case isotonic isn't a fallback-if-needed, it's the wrong default from the start.

**GBM validation must be country-stratified, not just k-fold — this was previously under-specified.** This document's bi-encoder section already evaluates on a held-out-country split (train US+India, hold out one as a France proxy) specifically because a random split can hide a model that's overfit to US/India-specific patterns while still scoring well on average. The GBM is the component most likely to pick up exactly that kind of shortcut — it's the one component in this pipeline that directly learns decision boundaries from labeled US/India pairs — yet its own early stopping (AUCPR), OOF calibration, and Stage 4 threshold search were previously specified only as generic k-fold, with no requirement that folds be country-aware. Fix: reuse the same held-out-country protocol already defined in [`08_open_decisions_log.md`](08_open_decisions_log.md) for the GBM's own early stopping, calibration, and threshold search — not only for the Stage 2a encoder-selection ablation it was originally scoped for. Concretely, run both: standard random k-fold as the primary CV, plus one held-out-country fold (train on US+India-minus-one, validate on the excluded one) as a diagnostic. If AUCPR or the chosen F₀.₅ threshold diverges meaningfully between the two, that gap **is** the GBM's overfitting signal for this task — a random-fold-only metric can look clean while still failing on France, since nothing about a random split forces the model to generalize across countries rather than just across records.

**Library choice:** XGBoost as the primary choice — mature, well-documented monotonic-constraint and DART support, and a safer default for an audited submission a reviewer needs to reproduce exactly. LightGBM is a reasonable fallback if training-time scaling becomes an issue.

**DART:** an escalation for generic overfitting (train/validation gap persisting after the regularization above), decided by the standard validation protocol — not a country-generalization-specific tool. Its connection to cross-country generalization is plausible (muting dominant early trees could reduce over-reliance on any single tree's country-specific shortcut) but speculative, and shouldn't be relied on in place of the targeted country-match masking above. Full citation and its relationship to the GBM's other regularization mechanisms — including the theoretical grounding for using a GBM as a meta-learner at all — is in [`05_regularization_and_anti_forgetting.md`](05_regularization_and_anti_forgetting.md).

**Feature attribution:** TreeSHAP, generated once training stabilizes — gives exact, fast attribution for a tree ensemble (unlike the approximations neural components would need), and backs the methodology document's feature-engineering section with real evidence rather than design intent alone.
