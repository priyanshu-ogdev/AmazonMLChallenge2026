# v1 baseline — the concrete plan for the 72-hour window

This supersedes the "Scope and timeline" note in `README.md` with the actual decided plan, not just a warning. Everything else in [`system_architecture.md`](../system_architecture.md)/[`04_bge_m3_training_spec.md`](04_bge_m3_training_spec.md)/[`05_regularization_and_anti_forgetting.md`](05_regularization_and_anti_forgetting.md) remains the *target* design; this file says what actually gets built first, in what order, and why each cut is safe.

## The four decisions, and why each is the cheapest available lever

**1. Superseded by the fine-tuning revision below — kept here for the record.** The original v1 decision was: Qwen3-Embedding-0.6B (off-the-shelf, no fine-tuning) replaces BGE-M3's dense head as the Stage 2a bi-encoder feature, verified directly (see [`07_citations_and_benchmarks.md`](07_citations_and_benchmarks.md)) against the PosIR Multilingual Retrieval benchmark (Qwen3-Embedding-0.6B beats BGE-M3 zero-shot on both English and French). This reasoning is **still correct as an off-the-shelf comparison** — it just no longer decides Stage 2a's primary feature, now that fine-tuning BGE-M3 is back in scope (see "Fine-tuning revision" below). Qwen3-Embedding-0.6B is kept as a free, inference-only second feature (**Stage 2a-ii**) rather than discarded.

**Implementation correction that still applies if Qwen3-Embedding-0.6B is used anywhere (as the fallback or the Stage 2a-ii auxiliary feature).** Qwen3-Embedding-0.6B is instruction-aware and built for asymmetric query→document retrieval: its own model card recommends an instruction prefix on the query side only (e.g. `"Instruct: Given a web search query, retrieve relevant passages that answer the query\nQuery: "`), with no prefix on the document side, and reports omitting it costs roughly 1–5% retrieval quality. **This pipeline's Stage 2a task is not query-vs-document — it's symmetric pairwise similarity between an S1 record and an S2/S3 candidate.** Neither side is a "query." Applying the default asymmetric prefix here would silently bias every score toward whichever side happened to get the instruction. Correct usage for this task: **the same treatment on both sides** — either an identical instruction on both records or no instruction on either side, decided by a quick same-day check on the training split. Do not use the model's default query/document asymmetry.

## Fine-tuning revision — time and hardware confirmed, LoRA promoted into v1 scope

The original cut assumed no confirmed hardware and no confirmed time slack for fine-tuning. Both are now confirmed (RTX 3060 12GB, real time budgeted). The full committed configuration — LoRA rank 64 on BGE-M3's dense head, VRAM budget math, and the four-layer France-regularization stack (LoRA rank ceiling, self-distillation anchor, country-balanced hard-negative mining, held-out-country gate) — is in [`04_bge_m3_training_spec.md`](04_bge_m3_training_spec.md)'s "Bi-encoder LoRA fine-tune" section, not duplicated here. The short version: BGE-M3 is already pretrained on 100+ languages including French (there's no separate "French BGE-M3" to find — it's the standard checkpoint), so fine-tuning adapts a base model that already has the coverage this competition's held-out country needs, provided the anti-forgetting stack actually protects it — which is what the held-out-country gate exists to confirm before the fine-tuned checkpoint is trusted over the off-the-shelf fallback.

**2. BGE-M3 stays blocking-only** — no change to [`system_architecture.md`](../system_architecture.md) Stage 1. Its dense+sparse+ColBERT output in one pass is still the reason it's there; that reasoning was never about which model wins the Stage 2a feature, so removing it from Stage 2a doesn't weaken Stage 1 at all.

**3. Qwen3-0.6B Generative Matcher (Stage 2b) is cut for v1**, remaining a stretch goal — replacing legacy Ditto designs, see [`04b_qwen3_generative_matcher_spec.md`](04b_qwen3_generative_matcher_spec.md). **Bi-encoder LoRA fine-tuning is promoted back into v1 scope** given confirmed RTX 3060 12GB availability and confirmed time budget — this reverses the original cut. See [`04_bge_m3_training_spec.md`](04_bge_m3_training_spec.md)'s "Bi-encoder LoRA fine-tune" section for the committed (non-swept) configuration, VRAM budget, and the four-layer France-regularization stack. Stage 2a's model also changes accordingly: **fine-tuned BGE-M3 dense head, rank-64 LoRA**, replacing the earlier off-the-shelf-Qwen3-Embedding-0.6B-only plan — with off-the-shelf Qwen3-Embedding-0.6B kept as a second, free (inference-only) feature (**Stage 2a-ii**) if time allows, rather than a forced either/or choice.

**4. Saved time goes to two things, in this order: the blocking-recall audit, then F₀.₅ threshold tuning.**

## Why these two are the right place to spend saved time — the actual math

**Blocking-recall audit first, because it's a hard ceiling, not a tunable.** [`system_architecture.md`](../system_architecture.md) Stage 1 already specifies this as a gate, but it's worth being explicit about *why* it dominates every other lever available in the remaining time: recall lost at blocking cannot be recovered by any amount of matching-stage sophistication, calibration, or threshold choice — a true match that was never placed in `candidate_pairs.tsv` scores zero for that entity's precision *and* recall, full stop. Every hour spent improving Stage 2/3/4 before this is checked is an hour that might be spent optimizing on top of an artificially capped ceiling. The check itself is cheap: one pass over `train_ground_truth`, computing for each S1 entity whether its true matches appear anywhere in the unioned candidate set, sliced by country (crucially, by the France-proxy country in the held-out split, not just the in-domain average). This is a single script, well under an hour to write and run, and it tells you immediately whether the address-token/phonetic blocking needs strengthening before anything else is worth doing.

**Threshold tuning second, because F₀.₅'s precision weighting makes the optimal cutoff genuinely far from the naive default, and getting it right costs almost nothing.** The formula, restated from the official problem statement: F₀.₅ = (1.25 × P × R) / (0.25 × P + R). At the naive 0.5 threshold, a GBM calibrated for balanced accuracy is not calibrated for a metric that weights precision 2× over recall — the optimal cutoff is provably higher than 0.5 whenever precision is increasing and recall is decreasing in threshold (true for essentially any reasonable calibrated classifier), and just how much higher is easy to get wrong by guessing. Concretely: at precision 0.7 / recall 0.9 (plausible for an under-tuned threshold), F₀.₅ = (1.25 × 0.7 × 0.9)/(0.25 × 0.7 + 0.9) = 0.7875/1.075 ≈ **0.7326**; nudging the threshold up to precision 0.85 / recall 0.75 (same model, higher cutoff) gives F₀.₅ = (1.25 × 0.85 × 0.75)/(0.25 × 0.85 + 0.75) = 0.796875/0.9625 ≈ **0.8279** — a **~13% relative improvement** in the actual scored metric (verified by direct calculation, not the earlier arithmetic error this replaces), from a threshold sweep that costs minutes once the GBM's calibrated probabilities exist, versus zero additional model training. This is the cheapest lever in the entire pipeline per hour spent, and [`system_architecture.md`](../system_architecture.md) Stage 4 already specifies k-fold CV for exactly this reason — the only change v1 makes is prioritizing it explicitly over LoRA sweeps/Stage 2b rather than leaving it implicitly scheduled last.

## Throughput sanity check for the off-the-shelf Qwen3-Embedding-0.6B swap

Public benchmarks report roughly 250 passages/sec on an A100 for the 4B model; the 0.6B model is smaller and should run faster on the RTX 3060 class hardware [`04_bge_m3_training_spec.md`](04_bge_m3_training_spec.md) targets, but to stay conservative, assume 100–150 pairs/sec at bf16 on a 3060 for short (name+address-length) strings. Encoding **candidate pairs**, not the full table — this only runs on `candidate_pairs.tsv`'s output, already narrowed by blocking — so for, say, 50,000 candidate pairs (a plausible order of magnitude for this dataset's scale), that's roughly 6–8 minutes of GPU time for the entire Stage 2a-ii feature column, off the shelf. This is a rounding error next to the time saved by skipping exhaustive LoRA sweeps and Stage 2b fine-tuning entirely, which confirms the swap is free in the time budget that matters.

## Revised v1 build order

1. Stage 0 (ingestion) + Stage 1 (BGE-M3 blocking, unioned with token/phonetic/address blocking) → **blocking-recall audit against `train_ground_truth`, sliced by country, before anything else**.
2. **Bi-encoder LoRA fine-tune** (rank-64, BGE-M3 dense head, config in [`04_bge_m3_training_spec.md`](04_bge_m3_training_spec.md)) — run the held-out-country gate (train US/validate India, reverse) before trusting the checkpoint; fall back to off-the-shelf BGE-M3 or Qwen3-Embedding-0.6B if the gate fails and there's no time to iterate on the regularization stack.
3. Stage 2a (fine-tuned BGE-M3 dense head, plus off-the-shelf Qwen3-Embedding-0.6B as Stage 2a-ii second feature if time allows) + Stage 2c (hand-crafted features) → GBM (Stage 3).
4. Stage 4 threshold search via k-fold CV, optimized for F₀.₅ specifically, prioritized immediately after the GBM trains — not deferred to "if time remains."
5. Stage 5 output assembly + `validate_submission.py`. **Two separate write-ups, not one** — see [`system_architecture.md`](../system_architecture.md)'s Stage 5 note on the two deliverables: (a) the Unstop Round-1 upload is a **1–2 page** approach summary, due within the 72-hour window, budget an hour or two for it, not more; (b) the full `Documentation_template.md` (no page limit, per the official problem statement) is only required in depth if the team advances to the audited final-package stage — don't front-load research-depth writing into the 72-hour window at the expense of steps 1–4 above.
6. **Stretch, only if steps 1–5 finish with time to spare:** Qwen3-0.6B Causal Generative Matcher (Stage 2b, per [`04b_qwen3_generative_matcher_spec.md`](04b_qwen3_generative_matcher_spec.md)), DART, TreeSHAP attribution — in that order of expected payoff per hour, per the reasoning already in [`04_bge_m3_training_spec.md`](04_bge_m3_training_spec.md)/[`05_regularization_and_anti_forgetting.md`](05_regularization_and_anti_forgetting.md).
